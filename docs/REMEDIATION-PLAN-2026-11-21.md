# Аудит и план: приоритеты 1, 2, 5

Дата: 2026-11-21 UTC. SSH, сертификаты и установка плагина в amoCRM в этот
план не входят.

## 1. FPM `www max_children`

### Что подтверждено

- Текущий пул: `www = 4`, `filehub_media = 4`, `filehub_operations = 2`,
  `filehub_auth = 2`.
- В `20 Nov 09:21:06` зафиксировано
  `[pool www] server reached max_children setting (4)`.
- В эту минуту пришло 34 запроса: 12 `POST /client-events`, 12
  `OPTIONS /client-events`, 4 `OPTIONS /files`, 4 `GET /files`, сессия.
- Все ответы были `200/204`; максимальная задержка `0.430 с`, ответов `5xx` и
  запросов дольше секунды не было.
- PHP-контейнер имеет лимит 192 MiB; текущее потребление по последнему
  измерению около 26.4 MiB. Запас памяти позволяет поднять `www` до 8.

### Причина

Пул `www` обслуживает интерактивные и телеметрические запросы. При открытии
многих карточек несколько вкладок одновременно отправляют диагностику, а
также параллельно запрашивают списки файлов. Четырёх worker-процессов хватает
не всегда; в пике образовывалась кратковременная очередь.

### Решение

- Поднять `pm.max_children` пула `www` с 4 до 8.
- Оставить остальные пулы без изменений.
- Обновить тест FPM и проверку live-конфига.
- Выполнять применение через существующий `apply-fpm.sh` с проверкой памяти,
  inode и фактического конфига контейнера.

## 2. Fan-out телеметрии из вкладок

### Что подтверждено

- Очередь телеметрии общая для контекста `account+operator`, хранится в
  `localStorage`, батч ограничен 10 событиями и 7 800 байтами.
- Всплеск `09:21` содержал 12 одновременных `POST /client-events`.
- Код использует `navigator.locks` с именем
  `czfh-telemetry-flush-v1:<contextKey>`, но `flushTelemetry()` вызывает
  `sendTelemetryBatch()` и сразу возвращает управление. Web Lock освобождается
  до завершения `fetch` и удаления подтверждённых событий из очереди.
- Поэтому другая вкладка может захватить тот же lock, снова прочитать тот же
  `localStorage` и отправить дублирующий батч. Это и есть основной fan-out.

### Решение

- Сделать `sendTelemetryBatch()` возвращающим Promise, завершающийся только
  после обработки ответа/ошибки и очистки очереди.
- Возвращать этот Promise из `run()` внутри Web Lock, чтобы lock удерживался
  до подтверждения батча.
- Добавить небольшой jitter к обычному таймеру 3.5 секунды, чтобы вкладки не
  просыпались строго одновременно.
- Сохранить прямой `keepalive`-путь для `pagehide`/`destroy`.
- Добавить регрессионный тест, что второй flush не стартует до завершения
  первого.
- Поднять версию виджета до `2.8.21` и пересобрать установочный ZIP.

## 5. Алерты

### Что подтверждено

- В runbook есть только пороги, но готового сборщика/таймера алертов нет.
- Нужно покрыть: `max_children`, любой `5xx`, `media_denied`, запросы дольше
  5 секунд.
- Nginx access log содержит статус, `request_time`, `request_id` и не содержит
  query string в самой структуре лога.
- FPM пишет `max_children` и `media_denied` в JSON-лог контейнера.

### Решение

- Добавить read-only Python-скрипт, который читает последние 10 минут
  `filehub_access.log` и JSON-лог PHP-контейнера.
- Дедуплицировать события через state-файл, чтобы таймер не повторял один и
  тот же алерт каждую минуту.
- Не выводить query string, подписи, токены и идентификаторы сделок.
- Писать алерты в `/var/log/filehub-alerts.log` и journal.
- Поддержать необязательный webhook через `FILEHUB_ALERT_WEBHOOK`.
- Добавить systemd service/timer с запуском раз в минуту и logrotate.
- Добавить тесты на 5xx, slow, max_children, media_denied, дедупликацию и
  отсутствие секретов в выводе.

## Порядок реализации

1. Изменить `www.conf` и FPM-тест: `www = 8`.
2. Исправить удержание Web Lock и добавить jitter; обновить версию/пакет.
3. Добавить alert checker, unit-файлы, установщик и тесты.
4. Прогнать `run-tests.sh` и проверить локальные артефакты.
5. Выдать root-команды для применения FPM и установки алертов; установка
   виджета в amoCRM остаётся отдельным действием.

## Критерии приёмки

- В конфиге и контейнере после apply: `www=8`, остальные пулы без изменений.
- В тесте телеметрии второй flush не отправляет данные, пока первый не
  завершился; батч подтверждается только после `2xx`.
- Alert checker выдаёт по одному алерту на событие/минуту, не содержит
  секретов и переживает отсутствие PHP-лога с предупреждением в journal.
- Все существующие и новые тесты проходят.
